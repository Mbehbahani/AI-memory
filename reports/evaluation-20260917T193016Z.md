raises **entity presence** (50.8% → 72.0%) — the related-entity names it adds are exactly what

top 5, and for several gold questions that reshuffling pushed the one expected source out of the
top 5 in favour of a different, also-plausible, entity-linked chunk. Both numbers are real; neither
is "the" recall number for this system.

## Product findings surfaced while building this gold set (NEEDS_HANDOFF — outside `tests/**`, not fixed here)

Building an honest gold set meant reading the real `facts`/`entities` tables directly, which surfaced
two extraction/ontology issues beyond retrieval ranking. Reported, not fixed — `packages/aimemory/**`
is outside this agent's owned paths.

1. **`HAS_OWNER`/`HAS_STATUS` subject and object appear reversed for person-centric episodes.**
   `docs/architecture/ontology.md` line 33 defines `Project → HAS_OWNER/HAS_STATUS → Person`, but
   MEASURED: of 58 `HAS_OWNER` facts, 38 have a `Person` entity (`Mohammad`/`Mohammad Behbahani`) as
   the **subject** and a project name as the free-text `object_value` (e.g. `Mohammad Behbahani
   HAS_OWNER "JobPilot"`); all 7 `HAS_STATUS` facts do the same (`Mohammad HAS_STATUS "Picnic"`,
   `Mohammad HAS_STATUS "AWS Cloud Quest"`, etc.). Because `HAS_OWNER`/`HAS_STATUS` are in
   `functional_predicates` (`ontology.md` §163, one *current* value per `(subject, predicate)`), every
   new project mention for the same person closes out the previous one — the `uq_facts_functional_current`
   unique index is presumably firing on `(subject_entity_id='Mohammad', predicate='HAS_OWNER')`. Net
   effect: only the most-recently-extracted project is ever "current" owner/status for Mohammad, and
   every earlier one reads `historical`, which is very likely not the intended semantics. Suggest A08
   (extraction prompt/direction) or A02 (ontology docs vs. schema) investigate whether the extractor is
   asked to emit these edges in the wrong direction, or whether the functional-predicate uniqueness
   constraint needs to key on the *project* subject instead.
2. **Some `USES_ARCHITECTURE` chains collapse genuinely-concurrent facts into one "current" value.**
   MEASURED: the `JobLab` entity has 10 `USES_ARCHITECTURE` facts (SvelteKit, Convex, Python, FastAPI,
   Supabase, PostgreSQL, Next.js, ECharts, Mantine, Bronze/Silver/Gold) and only the last-extracted one
   (`Bronze/Silver/Gold`) is `current`; the other 9 — including `SvelteKit`, which Q01 and the corpus's
   own `JobLab Overview.md` both still describe as JobLab's live frontend — are `historical`. This looks
   like the same functional-predicate-as-single-value assumption applied to what is, for
   `USES_ARCHITECTURE`, actually a multi-valued relationship (a project uses several technologies at
   once). `JobLab DE Lakehouse`'s own `USES_ARCHITECTURE` chain (Databricks Delta → Snowflake →
   Tableau, Q08 above) looks like genuine sequential migration by contrast, so this is not a blanket
   "the predicate is broken" claim — it is specific to entities/episodes where several concurrently-true
   technologies get extracted across one or more episodes and each closes out the last. Suggest A02/A08
   review whether `USES_ARCHITECTURE` (and possibly `DEPLOYED_ON`) should be excluded from
   `functional_predicates` or the extractor should be told to batch same-episode technologies into one
   fact/episode.
3. **Retrieval sometimes prefers generic high-overlap chunks over the specific document the question is
   about** (Q13, Q16, Q20, Q21 above: the expected chunk exists, is `INDEX_CONTENT`, `active`, and
   confirmed present via direct SQL, but did not rank in the top 5). Verified for Q20 specifically: the
   job posting `vault://my-vault/00 Inbox/job-positions/Data Scientist - Operations Research _ Action.md`
   has 68 indexed chunks, yet a generic CV-writing workflow template outranked it for a
   requirements-style question, apparently on keyword overlap ("job description", "requirement").
   Suggest A09 review whether `keyword_top_k`/RRF weighting needs adjustment for short, specific
   documents competing against long, generic ones that happen to share vocabulary.

## Limitations of this run (honest, not swept under the rug)

- `expected_timeline_order` questions (e.g. Q08) can fail even when the underlying `facts.supersedes_fact_id` chain is correct, because several real facts share one `valid_from` timestamp (extraction time was used as a fallback, not a date stated in the text) — `score_temporal_order`'s stable sort then cannot recover the intended order. This is a real, measured property of the current corpus, not a scorer bug.
- Q04 and Q06 (owner-authored, left unmodified) reference a JobLab DE `localfs://` source and the `mini-vault` fixture respectively; the corpus this run queried is vault-only (the JobLab DE repo has not been ingested) and this script does not stand up a fixture corpus (see module docstring), so Q04 is expected to score poorly and Q06 is skipped rather than silently passed.
- `expected_types` matching is a best-effort substring check against hit text/title (see `scorer.score_expected_types`), not a guarantee the returned object is literally that artifact type — a look at the per-question table plus the raw response is the ground truth.
