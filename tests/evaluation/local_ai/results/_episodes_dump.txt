# JobLab DE Lakehouse

The data-engineering half of JobLab. Takes a weekly read-only export of the live JobLab job-market data and rebuilds it as a proper analytical lakehouse — **PySpark medallion → Databricks Delta → Snowflake → Tableau Public** — without ever touching the live product.

Public repo: [joblab-lakehouse](https://github.com/Mbehbahani/joblab-lakehouse)

## What it is

- **Contract-first, current-snapshot.** No fabricated history. A weekly check either finds the data unchanged (no-op) or changed (the single active snapshot is validated and atomically replaced). Historical trend marts were explicitly ruled out — three weeks of scrapes cannot honestly support trend claims.
- **Evidence over existence.** A phase is only "done" with reconciled row/key counts, schema fingerprints, and deterministic logical checksums that stay identical across reruns. Passing code is not evidence.
- **Built by a governed AI agent team.** An Opus lead agent (`de-lead`) orchestrating Sonnet specialists for Databricks, Snowflake, and docs — each gated behind a pre-flight access checklist so no agent touches a real cloud account or spends money unprompted.

## Where it stands

| Phase | What happened |
|---|---|
| 0–2 | Local setup, accepted Supabase baseline (20,209 rows, reconciled + hashed), weekly conditional refresh |
| 3 | Local PySpark Bronze/Silver/Gold — 8 Gold products, all validated as DataFrames |
| 4 | Reproduced in **Databricks Free Edition** — 13 Delta tables + the project's first real physical Gold Parquet write |
| 4a | Native **Databricks AI/BI dashboard** (2 pages, 19 widgets, gold-only sourcing) |
| 5 | **Snowflake** serving — least-privilege roles, X-Small warehouse w/ 60s auto-suspend, resource monitor, full reconciliation |
| 6 | **Tableau Public** dashboard published — see [[Tableau Public Profile]] |

Total cloud spend so far: **$0** (Databricks Free Edition, Snowflake trial allowance — 0.07 of 5 credits used).

## 1. Repo identity (the GitHub "About" panel)

The right-hand panel on a repo page is the **portfolio shopfront**. Every field must be filled.

### 1.1 Description (1 sentence, ≤ 160 chars)

Formula:

```
<What it is> for <who/what problem>, with <distinguishing technical features>.
```

**Rules:**

- Start with a concrete noun phrase, not a verb (e.g. *"AI-powered job orchestration platform…"* not *"Builds…"*).
- Name the *domain* and the *technical distinctiveness* in one breath.
- No emojis. No marketing fluff. No trailing period inside the GitHub field.
- Avoid throwaway adjectives ("simple", "small", "test").

**Good examples** (from current repos):

- *AI-powered job orchestration platform with Kanban workflows, LLM agents, and production-oriented system architecture.*
- *Enterprise RAG architecture and evaluation repository for regulated tax-domain QA — secure OpenSearch retrieval, Bedrock-based grading, zero-hallucination citation design, and Jaeger observability.*
- *FastAPI backend for AI-powered job search, CV matching, and chat-based workflow automation.*

**Bad (do not ship):** *"Needs description"*, *"My project"*, *"Official code for the research paper"* without context.

### 1.2 Website URL

- Production app → product domain (e.g. `jobflow.oploy.eu`).
- Library / API / demo → docs site or deployed demo.
- Research / study repo → blog post, paper landing page, or YouTube video URL.
- No public surface → leave blank rather than linking the GitHub URL itself.

### 1.3 Topics (5–10 tags)

See [[About and Topics Cheatsheet]] for the controlled vocabulary. Rules:

- Always include **one domain tag** (`ai-engineering`, `rag`, `optimization`, `data-engineering`, `decision-intelligence`, `operations-research`).
- Always include **the primary framework / runtime** (`fastapi`, `nextjs`, `sveltekit`, `nuxt`, `matlab`, `r`).
- Always include **deployment / infra** when relevant (`aws`, `aws-lambda`, `docker`, `vercel`, `convex`, `railway`).
- Always include **product family** for product repos (`oploy`, `joblab`, `jobpilot`, `hmm-rem`).
- Lowercase, hyphen-separated. No marketing tags (`awesome`, `cool`).

### 1.4 Resources (sidebar toggles)

| Toggle | Required | Notes |
|---|---|---|
| Readme | ✅ always | See section 3 |
| License | ✅ public repos | MIT for libraries/portfolio; private may omit |
| Code of conduct | optional | Only when accepting external PRs |
| Citation | ✅ research repos | `CITATION.cff` with paper DOI |

### 1.5 Releases, Packages, Deployments

- **Releases:** Tag `v0.1.0`, `v1.0.0`, … for any repo a stranger might `pip install` / `npm install` / clone for a demo. Include a 3–5-bullet release note.
- **Packages:** Publish only when the repo has a real consumer; otherwise leave empty.
- **Deployments:** GitHub auto-populates from CI/CD — keep the production environment named `production` so the panel reads cleanly.

# Ubuntu Server Setup and Usage Guide

A step-by-step tutorial for setting up and operating the Ubuntu Server 24.04 box (on the Huawei
laptop) from this Windows laptop — written so the whole thing can be redone from scratch if needed,
or just used as a reference for day-to-day tasks.

For the AI-assistant-facing version of this (current IP, live status, exact reconnect commands),
see `D:\Account Center\Huawei\README.md` — that file is kept up to date automatically; this guide
explains the *why* and *how* behind it, step by step, for a person following along.

---

## 1. Connecting the Ubuntu server to the internet (WiFi)

The server has no ethernet cable — it needs to join the building's WiFi.

1. On the Ubuntu machine's own keyboard/screen, log in and check the WiFi adapter's name and status:
   ```
   ip a
   ```
   Look for an interface like `wlp0s20f3`. If it has no `inet` line, it isn't connected yet.

2. Ubuntu **Server** (unlike Desktop) doesn't ship with `nmtui`/NetworkManager — it uses **netplan**
   instead. Check for existing config:
   ```
   ls /etc/netplan/
   ```

3. Create a WiFi config file:
   ```
   sudo nano /etc/netplan/01-wifi.yaml
   ```
   Type this, replacing the network name and password with the real WiFi credentials (mind the
   indentation — 2 spaces per level, exactly):
   ```yaml
   network:
     version: 2
     wifis:
       wlp0s20f3:
         dhcp4: true
         access-points:
           "YOUR_WIFI_NAME":
             password: "YOUR_WIFI_PASSWORD"
   ```
   Save with `Ctrl+O` then Enter, exit with `Ctrl+X`.

   Tip: if this laptop (the Windows one) is already on the same WiFi, you can read its saved
   password instead of hunting for it: open PowerShell and run
   `netsh wlan show profile name="NETWORK_NAME" key=clear` — look for "Key Content".

4. Apply it:
   ```
   sudo netplan apply
   ```

5. Verify:
   ```
   ip a
   ```
   You should now see an `inet 192.168.x.x` or `10.x.x.x` line under `wlp0s20f3`. That's the
   server's local IP — write it down, you'll need it for every SSH connection below.

---

## 2. Setting up SSH so you can control it from this laptop

1. On the Ubuntu server, install and enable the SSH server:
   ```
   sudo apt update
   sudo apt install openssh-server -y
   sudo systemctl enable --now ssh
   ```

2. On the Windows laptop, open PowerShell and connect (replace with the real IP):
   ```
   ssh sohamoha@10.130.231.5
   ```
   First time, type `yes` to accept the fingerprint, then enter the account password.

3. **Set up passwordless login** (so you never have to type the password again). On the Windows
   laptop, generate a key if you don't have one:
   ```powershell
   ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\id_ed25519" -N '""'
   ```
   Then copy the public key to the server (this one time still needs the password):
   ```powershell
   type "$env:USERPROFILE\.ssh\id_ed25519.pub" | ssh sohamoha@10.130.231.5 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
   ```
   From now on, `ssh sohamoha@<ip>` connects with no password prompt at all.

4. **(Optional) passwordless sudo** — only do this if you want a tool/assistant to run admin
   commands on this box without you typing the sudo password every time. Skip this on any machine
   where that risk isn't worth it.
   ```powershell
   ssh -t sohamoha@10.130.231.5 "echo 'sohamoha ALL=(ALL) NOPASSWD:ALL' | sudo tee /etc/sudoers.d/90-sohamoha-nopasswd && sudo chmod 440 /etc/sudoers.d/90-sohamoha-nopasswd && sudo visudo -c"
   ```

##### E11 00 Inbox/web-extention/Monitor AI coding agents with Grafana.md 3477
AI coding agents — GitHub Copilot, Claude Code, OpenClaw, and others — are quickly becoming part of how engineering teams ship software. Adoption is the easy part. The harder questions follow soon after:

- **How much are we spending?** Which models, which teams, and which tasks drive the cost?
- **Who is actually using which agent, and for what?** Are tools being invoked the way you expect?
- **Is the experience reliable?** Where do agents stall, error out, or leave sessions stuck?
- **Can we audit what the agents did?** Prompts, tool calls, and model choices for security and compliance review.

Grafana gives you a single pane of glass for these questions across multiple coding agents. This guide walks through the setup end-to-end: standing up the telemetry pipeline, pointing each agent at it, and importing the ready-made dashboards.

## What you'll see

Three purpose-built Grafana dashboards visualize the signals that matter for AI coding agents — cost, token consumption, sessions, model usage, tool invocations, latency, and errors:

| Dashboard | What it shows | Link |
| --- | --- | --- |
| [GitHub Copilot](https://aka.ms/amg/dash/gh-copilot) | Operations, input/output tokens, chat sessions, tool calls, response time and TTFT by model | `aka.ms/amg/dash/gh-copilot` |
| [Claude Code](https://aka.ms/amg/dash/claude-code) | Cost, sessions, user prompts, API requests/errors, daily cost and token trends, per-model breakdown, tool usage analytics | `aka.ms/amg/dash/claude-code` |
| [OpenClaw](https://aka.ms/amg/dash/openclaw) | Messages, unique chats, response time, LLM calls, token usage, cache reads, stuck sessions, model usage breakdown | `aka.ms/amg/dash/openclaw` |

![Screenshot of the Claude Code dashboard in Grafana, showing cost, sessions, daily cost and token trends, per-model breakdown, and tool usage analytics.](https://learn.microsoft.com/en-us/azure/managed-grafana/media/grafana-opentelemetry-app-insights/claude-code-main.png)

Screenshot of the Claude Code dashboard in Grafana, showing cost, sessions, daily cost and token trends, per-model breakdown, and tool usage analytics.

## Who this guide is for

The same dashboards serve different audiences:

- **Platform and developer experience teams** — track adoption trends, spend by team and model, and surface inefficient usage patterns.
- **Engineering leaders** — correlate agent activity with delivery and answer "is this investment paying off?"
- **Security and governance teams** — review prompts, tool invocations, and model choices for compliance and risk.
- **Individual developers and on-call engineers** — debug agent behavior, slow tool calls, or stuck sessions.

## How it works

![Diagram explaining the agent flow.](https://learn.microsoft.com/en-us/azure/managed-grafana/media/grafana-opentelemetry-app-insights/grafana-coding-agent-diagram.png)

Diagram explaining the agent flow.

- Each **AI coding agent** (GitHub Copilot, Claude Code, or OpenClaw) emits OpenTelemetry traces, metrics, and logs to a configured OTLP endpoint.
- An **OpenTelemetry Collector** terminates OTLP at that endpoint and forwards the data to Application Insights using the Azure Monitor Exporter.
- **Grafana** queries Application Insights via the Azure Monitor data source (Log Analytics / KQL) to render the dashboards.

The OpenTelemetry Collector and the Application Insights pipeline are infrastructure — a one-time setup. The rest of this guide walks through it.

## Platform facts worth remembering

- **Everything is public.** No private/unlisted option on the free tier. Anyone with the link, or browsing the gallery, can view it.
- **Viewers can download the underlying data by default** unless you explicitly disable it in the workbook settings. Check this every time you publish.
- **No live database connections.** Tableau Public requires *extracts* — a static snapshot baked into the workbook. You cannot connect a published viz to Snowflake/Databricks live.
- **No scheduled refresh.** To update a published viz you re-export the data, refresh the extract locally, and republish manually.
- **Embeddable.** The Share button gives an iframe/embed snippet that works on any personal site or portfolio page.
- **Two desktop apps exist:** full *Tableau Desktop* (paid/trial, all connectors, publishes via the Server menu) and *Tableau Public Desktop* (free, file-based connectors only, publishes via `File → Save to Tableau Public`). Only the second is needed for this workflow.

## Gotchas hit while building

- **CSV delimiter auto-detection is unreliable** for small files — Tableau guessed `_` and then ` ` as the delimiter instead of `,`, shredding the headers into `F1, F2, F3...`. **Fix: use `.xlsx` instead of `.csv`** — Excel has explicit cells, so there is no delimiter to guess.
- **Sheets with identical column shapes get auto-unioned** when dropped on the same Data Source canvas (producing a broken `sheetname+` object). Fix: add each sheet as its own separate data source via `Data → New Data Source`, one at a time.
- **Number formatting lives on the field, not the mark.** Right-clicking a value in the view opens the *Font* panel. To format percentages: right-click the **pill** → `Default Properties` → `Number Format`.
- **Publishing requires extracts** — `Data → [source] → Extract Data...` for every data source before `Save to Tableau Public` will succeed.
- **If desktop publishing times out repeatedly** (`Error Code: DE1E797E`), fall back to `File → Export Packaged Workbook` (`.twbx`) and upload it through the browser at public.tableau.com. Caveat: browser upload publishes *every* sheet as a tab, with no sheet-selection step.
